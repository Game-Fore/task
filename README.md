# Smart Logistics: ставки на грузоперевозки

Тестовое задание Middle Data Engineer для «Умной Логистики». Пайплайн забирает сделки из операционной базы,
чистит их, считает рыночный коридор ставок по маршрутам и обучает модель, которая прогнозирует ставку перевозчика.

## Запуск

```bash
docker-compose up --build
```

При первом старте PostgreSQL генерирует источник `deals_bigdata` (300 000 сделок) и создаёт пустое хранилище `dwh`.
Потом сервис `pipeline` по очереди выполняет `etl migrate`, `etl load`, `etl mart`, `ml train`, `ml score` и
завершается. С нуля всё занимает около полутора минут. Каждый шаг идемпотентен, повторный `docker-compose up`
ничего не задваивает. Настройки лежат в `.env.example`; без `.env` берутся те же значения по умолчанию.

Перезагрузить период (окно по `loading_date`, границы включительно) и пересчитать витрину с этого месяца:

```bash
docker compose run --rm pipeline python -m etl load --start-date 2026-10-01 --end-date 2026-10-31
```

```bash
docker compose run --rm pipeline python -m etl mart --start-date 2026-10-01
```

Тесты (87 штук, поднимают свои временные базы на том же сервере):

```bash
docker compose run --rm pipeline pytest
```

## Стек

- **PostgreSQL 17** — и источник, и хранилище: две базы в одном контейнере. ETL ходит в источник по сети,
  как в настоящую внешнюю OLTP-базу, а отдельный контейнер ради этого не нужен.
- **Python 3.12 + psycopg 3** — перенос данных через `COPY`, трансформации написаны на SQL и выполняются
  внутри базы. Так 300 тыс. строк не гоняются через pandas туда и обратно.
- **Оркестратор** — пока обычный shell-скрипт `docker/run_pipeline.sh` с последовательными шагами. Шаги — это
  отдельные CLI-команды с параметрами окна, их без изменений можно вызвать из Airflow.
- **CatBoost** — основная модель: сам работает с категориями (регионы, кузов) и хорошо ловит нелинейность
  «расстояние × вес × кузов». **Ridge** из scikit-learn — линейный бейзлайн для сравнения.

## Как устроено

```
deals_bigdata ──COPY──► raw ──SQL──► core ──SQL──► mart.route_month_stats ──► view mart.mart_route_card
                                       │
                                       └──► ml train ──► ml score ──► mart.ml_price_predictions
```

- `raw` — копия таблиц источника как есть: сделки за окно, справочники целиком.
- `core` — очищенные данные: курс и `price_rub`, заполненные категории, справочник городов без дублей,
  группы кузова, помесячные даты сделок и карантин.
- `mart` — витрина маршрутов и прогнозы модели.

Загрузка окна (`etl/load.py`) — одна транзакция: удалить окно в `raw` и `core`, заново скопировать из источника,
прогнать проверки качества и разложить строки по `core` и карантину. Если что-то упадёт, останется прошлое
состояние. Источник читается в `REPEATABLE READ`, чтобы все таблицы пришли из одного снимка.

### Качество данных

Правила лежат списком в `etl/dq_rules.py`. Строка, нарушившая хоть одно, уходит в
`core.dq_quarantine_prices` со всеми причинами сразу и с исходной строкой в `jsonb`.

`PRICE_NON_POSITIVE`, `RUB_PRICE_LE_1000`, `DISTANCE_NON_POSITIVE`, `WEIGHT_NEGATIVE`, `VOLUME_NEGATIVE`,
`LOADING_CITY_UNKNOWN`, `UNLOADING_CITY_UNKNOWN`, `UNSUPPORTED_CURRENCY`, `FX_RATE_DATE_MISSING`, `FX_RATE_NOT_FOUND`.

На сгенерированных данных: из 300 000 строк в `core.prices` попадает 299 797, в карантин 203
(164 с ценой ≤ 0 и 39 валютных без даты курса). Остальные правила на этих данных не срабатывают ни разу,
их проверяют тесты.

### Витрина

Зерно: месяц × город отправления × город назначения × группа кузова × весовая категория.
В `mart.route_month_stats` хранятся P25 / медиана / P75 / среднее за рейс, P25 / медиана / P75 за км,
`trips_count`, `carriers_count`, `cv_rate`. Представление `mart.mart_route_card` добавляет `mom_pct`, `yoy_pct`
и `reliability_level`.

В выборку попадают факты (`price_type` 1, 2, 3, 4, 5, 9), без `complex` и без `outlier_mark`, с датами
`price_dates.price_date` не позже 26.10.2026. Месяц берётся из `price_dates`, поэтому долгосрочная заявка
попадает в несколько месяцев.

Всего 203 644 ячейки с 2023-10 по 2026-10: `HIGH` — 10, `MEDIUM` — 924, `LOW_DATA` — 202 710. Витрина очень
разреженная, в 78 % ячеек одна сделка. При таком зерне и 300 тыс. сделок это ожидаемо, поэтому у каждой строки
есть `trips_count` и `reliability_level`.

```sql
-- направления за октябрь с достаточной выборкой
SELECT loading_city, unloading_city, body_group, weight_category,
       p25_trip, median_trip, p75_trip, median_km, trips_count, carriers_count, mom_pct, yoy_pct, reliability_level
FROM mart.mart_route_card
WHERE month = DATE '2026-10-01' AND reliability_level <> 'LOW_DATA'
ORDER BY trips_count DESC;

-- история одного маршрута
SELECT month, p25_trip, median_trip, p75_trip, median_km, trips_count, carriers_count, cv_rate, mom_pct, yoy_pct
FROM mart.mart_route_card
WHERE loading_city = 'Москва' AND unloading_city = 'Ростов-на-Дону'
  AND body_group = 'Тент' AND weight_category = 'FTL'
ORDER BY month;

-- сверка ячейки с core: должно получиться 112 | 126991.51, как в витрине
SELECT count(DISTINCT p.price_id),
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY p.price_rub)::numeric, 2)
FROM core.prices p
JOIN core.price_dates d       ON d.price_id = p.price_id AND d.month = DATE '2026-10-01'
JOIN core.price_body_groups g ON g.price_id = p.price_id AND g.body_group = 'Тент'
WHERE p.loading_city_gcid = 1001 AND p.unloading_city_gcid = 1008 AND p.weight_category = 'FTL'
  AND p.is_fact AND NOT p.complex AND NOT p.outlier_mark AND d.price_date <= DATE '2026-10-26';
```

### ML

Предсказываем `price_rub` — ставку за рейс без НДС. Разбиение по `loading_date` от даты снимка 26.10.2026:

| Выборка | Даты погрузки | Строк |
|---|---|---|
| train | 26.07 – 04.10.2026, без выбросов | 24 226 |
| test | 05.10 – 26.10.2026, без выбросов | 12 808 |
| прогноз | после 26.10.2026, все плановые заявки | 4 891 |

Признаки: расстояние; регион, город и координаты отправления и назначения по отдельности; вес, объём,
группа и код кузова, весовая и объёмная категории; год, месяц, день недели, день года и их sin / cos.

Метрики на test, получены прогоном:

| Модель | R² | MAPE | RMSE, руб. | MAE, руб. |
|---|---|---|---|---|
| CatBoost (`catboost_v1`) | 0.9165 | 16.13 % | 55 286 | 28 700 |
| Ridge (`ridge_v1`) | 0.8404 | 49.42 % | 76 416 | 48 316 |

Повторное обучение даёт те же прогнозы до копейки. Больше всего весят расстояние (60 %) и вес (19 %). География
даёт меньше 3 %: в сгенерированных данных цена от региона не зависит.

Прогнозы обеих моделей лежат в `mart.ml_price_predictions`: test-период и будущие заявки. У будущих
`actual_price_rub`, `abs_error_rub` и `ape_pct` пустые. Метрики можно пересчитать прямо из таблицы:

```sql
WITH t AS (
    SELECT model_name, actual_price_rub AS y, predicted_price_rub AS p, ape_pct, abs_error_rub,
           avg(actual_price_rub) OVER (PARTITION BY model_name) AS y_mean
    FROM mart.ml_price_predictions
    WHERE loading_date <= DATE '2026-10-26'
)
SELECT model_name, count(*) AS test_rows,
       round(1 - sum((y - p) ^ 2) / sum((y - y_mean) ^ 2), 4) AS r2,
       round(avg(ape_pct), 2)                                AS mape_pct,
       round(sqrt(avg((y - p) ^ 2)), 2)                      AS rmse_rub,
       round(avg(abs_error_rub), 2)                          AS mae_rub
FROM t GROUP BY model_name ORDER BY model_name;
```

## Решения и допущения

**Загрузка**
- Идемпотентность — перезапись окна целиком (`DELETE` + `INSERT` в одной транзакции). В отличие от upsert,
  так исчезают и строки, которые пропали из источника.
- В `core` остаются все сделки, прошедшие проверки, включая ставки торгов и составные маршруты. Это не мусор,
  а другой scope, отфильтровывают их витрина и модель.
- Рубли пересчитываются по курсу 1.0, даже если `nearest_rate_date` пустой (1 428 строк). Доллары и евро — только
  по курсу точно на `nearest_rate_date`, без подстановки других дат.
- Правило «цена ≤ 1000» действует только для рублей.
- Совпадение городов погрузки и выгрузки ошибкой не считается.
- Весовая и объёмная категории заполняются только там, где они пустые. Вес округляется до 0,1 т на `numeric`,
  поэтому 9.95 т — это уже FTL.
- Дубли городов по `gc_id` убираются выбором строки с минимальным `id`, первичный ключ не даст им вернуться.
- Группы кузова: у сделки может быть несколько групп (например, тент и борт), в каждой она учитывается один раз.
  Если связей в `price_body_types` нет, берётся `prices.body_type`, если и его нет — «Не указан». Для модели
  нужна одна группа, это группа `prices.body_type`.

**Витрина**
- Дата снимка `AS_OF = 2026-10-26` задаётся параметром, системное время нигде не используется.
- Перцентили — `percentile_cont`, с интерполяцией, как в numpy и pandas по умолчанию.
- Пересчёт витрины идёт с месяца `start-date` до `AS_OF`, а не только по окну загрузки: долгосрочная заявка
  живёт и в следующих месяцах.
- MoM и YoY считаются в представлении и сравнивают только с календарно соседней ячейкой. Нет ячейки — NULL.
- «Свежая» ячейка для `HIGH` — последняя сделка в ней не старше 30 дней от `AS_OF`.
- `volume_category` в витрину не вошла: у ячейки нет одного значения.

**Модель**
- Утечки исключены устройством кода: модель читает только `core`, где нет `price_group_stats`, цены с НДС
  и маржи; признаки заданы белым списком, от цены не считается ни один.
- `outlier_mark` только убирает выбросы из train и test, признаком не является.
- Препроцессинг Ridge собран в один `Pipeline` и обучается только на train. CatBoost кодирует категории сам
  и тоже видит только train.
- Гиперпараметры зафиксированы, без early stopping: подбирать их по test было бы подглядыванием.
- `price_type` в признаки не взят: его нет ни в задании, ни в отчёте. При этом он известен заранее и, скорее
  всего, улучшил бы точность.
- Дополнительной чистки выбросов нет: общий межквартильный размах по цене резал бы дальние рейсы, а не аномалии.

## Ограничения

- Ночная разметка выбросов не прошла по записям, созданным 26.10 после 02:30. Проверил: все 5 790 таких строк —
  будущие погрузки, в историю и в обучение они не попадают. Но около 0,4 % выбросов генератор не размечает
  вообще, они остаются в витрине и в выборках.
- Сезонность модель не выучит: train покрывает только конец июля — начало октября. Для заявок на ноябрь–февраль
  она по сути переносит уровень цен из конца train. Нужна история хотя бы за год.
- MAPE 16 % близко к пределу для этих данных: судя по коду генератора, в цену заложен случайный шум около 13 %.
- В источнике нет индекса по `loading_date`, поэтому выгрузка окна читает `prices` целиком. На 300 тыс. строк
  это незаметно, на больших объёмах нужен индекс или выгрузка по `updated_at`.
- Если у сделки в источнике поменяется `loading_date`, её старая копия останется в прежнем окне, и загрузка
  нового окна упадёт на первичном ключе. Для меняющихся данных нужен CDC.
